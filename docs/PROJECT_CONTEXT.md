# GameWise AI 长期项目背景

本文件记录用户与 ChatGPT 前期讨论后确定的产品方向、技术方案、工程学习目标与合作原则，用于跨任务持续参考，避免依赖聊天上下文。技术名称保留英文。背景记录不等于功能已实现，也不构成执行后续全部任务的授权。

## 一、项目定位

GameWise AI 是一个面向普通玩家的多游戏、多版本、基于证据的 AI 攻略及比较助手。

它要解决通用大模型回答具体游戏机制、道具、Boss 和不同版本问题时，容易混淆游戏、编造规则、缺少可核查来源的问题。系统通过可靠资料与 RAG 支持回答，并使玩家能够检查证据与适用范围；不承诺完全消除错误。

## 二、产品能力与知识覆盖

当前执行顺序以用户最新要求为准：三服全目录武将持续后台采集，规则整理、检索实验和问答工程并行推进，不等待全量采齐。规则保存带来源的文件，武将身份和模式走结构化查询；全量收录目标保留，正式问答支持范围仍取决于审核及验证结果。

首版以完成项目与工程学习为优先，验证受控查询、模型问答、比较、引用、异常处理、网页与测试的闭环；不要求专家级策略评估或大规模统计。全量武将收录与有限开发测试并行，不能把演示题目范围当作资料收录目标。原始采集、结构化入库、审核可回答分别统计；收费模型、依赖和资料发送范围仍须确认。

主要工程成果应能用实际代码、调用记录、测试和评测结果讲清楚。利用LLM对明确技能与规则进行条件化分析，不提前手工编码所有强度判断；效果差的具体案例再补资料或流程。规则向量检索已按用户要求提前开展小规模对照实验，具体结果不预设优劣。简历描述与实测成果一致，不虚构性能或把模型能力归为自研模型能力。

针对间歇 HTTP 567，用户最新明确要求持续等待，不因重试次数耗尽退出：启用 --wait-on-567，等待依次为60、120、240、480、900秒，此后每900秒重试；服务器要求更久则遵守。429仍有限重试，403直接暂停；保留断点与错误记录，不改身份、Cookie或代理。此决定替代此前567最多重试两次的约定，不代表已确定错误原因或网站必然恢复。

评价须区分数值强度、特定身份与模式下的适应性、技能设计体验和人物还原。多摸牌、直接伤害等仅是待结合成本、触发条件、规则与对局环境分析的因素，不能存成无条件高低结论；人物还原需要角色背景依据，设计评价要说明判断标准。示例“刘备和曹操谁适合做主公”应能按服、具体系列、模式分别取双方技能及相关规则，并披露未收录项，不能只凭技能名称或模型常识下结论。

1. 根据玩家问题识别游戏及版本；必要时请求澄清，不自行猜测影响答案的范围。
2. 查询可靠资料，通过 RAG 生成有证据支持的回答。
3. 引用关联具体资料片段、来源链接、游戏和版本，使结论能够回溯到支持它的证据。
4. 缺少证据时明确表示无法确定，不编造规则、数值、来源或确定结论。
5. 支持跨游戏、跨版本的结构化比较，分别获取双方证据，明确每侧的适用范围和资料缺口。
6. 区分可验证的事实与主观评价；推断和策略建议也应明确标识。
7. 用户于 2026-10-28 调整首批 MVP：专注三国杀 OL、十周年、移动版三个发行分支，每个服记录各武将不同系列的技能。以此完成资料收集、RAG、有来源问答、跨服技能对照和评测的完整实验。黑暗之魂 3（Dark Souls III）与艾尔登法环（Elden Ring）保留成果并延后；长期多游戏架构不变。
8. 游戏登记不代表知识库已建成，必须明确显示已验证覆盖范围、未覆盖主题与资料状态；不假设任一游戏拥有完整攻略。

上述能力是产品方向。每一项的具体实现边界和首批验收范围应体现在 PRD 与小任务中；存在差异时提交用户决定，不以本文件为由一次实现全部功能。

用户进一步澄清：统一提问入口容纳问答及比较，不预设独立比较页面、接口或固定比较表。首批三个服用于验证通用流程，不能写死在核心。目录区分类别、发行分支、武将系列条目、模式、规则适用期和覆盖；不同系列不是同一条目的别名，系列关联须核查，不能只凭名字前缀猜测。人物或类别关联不表示规则共享。后续魂系仍可扩充黑暗之魂 1/2/3 等，采用游戏配置和必要的小型适配层。

用户进一步确认系列分类以页面“武将包／国战包”的实际名称记录，关联所属服和模式；普通/标准称呼不覆盖原始包名。三服谋包名称不同，不凭“谋”前缀统一归类；人物关联（如孙坚的不同条目）与包分类是两种关系。字段规则见 DATA_DESIGN，已有两服孙坚样本包提取和离线精确筛选，未建立完整知识库。

用户已实地核实本批页面的“经典/经典版本、国战、1V1”对应规则模式，经典不是原画分类，当前 mode 设计保留。每条具体武将规则记录只对应一个模式；普通孙坚等同名对象在不同模式下分别保存，即使技能文字相同也不合并。闪/谋/界孙坚的本次模式说明不扩展为所有同前缀武将的通用推断规则。

后续用户明确模式分类规则：国战归国战、1V1 归 1V1，其余武将系列不论前缀或包名都归经典，自走棋暂不处理。此规则更新此前对模式归类的保守约定；具体武将身份及系列关联仍须依据页面或明确映射，不能把“界限突破”直接当成模式。同一网页可以包含多个具体武将系列，下载整页不代表各系列已提取。

采集 OL 界曹操、界刘备时另发现“统率版本”规则章节，用户明确暂不收录，保留排除说明，不并入经典。实施顺序调整为先批量处理 OL、移动版，十周年同页多系列及跳转排版随后集中适配，已有成果保留；同一已授权的公开 Wiki 小批采集无需反复确认联网，遇站点拒绝仍停止并检查。

当前首批边界：玩家可直接自然语言提问，单个 LLM 选择受控只读工具，后端校验并执行查询，再根据证据回答（ReAct 思路）。未指定服的三国杀问题默认分别查询登记的三服，指定服则限定该服；“孙坚”查各服名称匹配条目，其他系列只列相关项，“孙坚各系列”才展开经核查关联。模式分别标注，规则范围不猜测，真实歧义再澄清。此决定替代此前“首批必须手动选服、自动识别延后”的约定；手动选择可作为辅助。完成至少一个真实跨服技能对照及隔离测试，跨游戏及完整历史版本对照延后，不建设多 Agent。首批三服各武将系列技能目标不变，分批实施，14 阶段不是两周收齐的承诺。

Day 1 已验收并本地保存；Day 2 已有元数据校验、魂系清单、BWIKI 两服孙坚提取实验及三服候选目录。用户初步认可目录，补充跨服条目的线下扩展关联，并确认未上线武将也收录：OL 闪孙坚标已上线，移动版起孙坚标未上线，保留用户确认及“敬请期待”等依据；上线状态与技能审核分开，后续随新证据更新。候选页面不代表已实装或正式知识覆盖，复杂关联及规则适用期仍待审查。正式知识库、游戏问答和评测尚未开始；健康接口与提取成功不代表 RAG 可用。实际进度以 PLAN.md 为准，测试夹具和模型替身不能证明真实知识覆盖或生成效果。

## 三、已确定的技术方案

| 领域 | 方向 | 仍需验证或确定的细节 |
| --- | --- | --- |
| 前端 | React + TypeScript + Vite | 已使用 Vitest、React Testing Library、jsdom；后续问答交互待设计，实际依赖见 frontend/package.json |
| 后端 | Python + FastAPI + Pydantic | 业务规则、数据结构和接口契约 |
| 原始资料 | 经过审核的 Markdown / JSON | 来源、版本适用性、覆盖主题和使用范围 |
| 结构化数据 | 优先 SQLite | 最小表结构、约束与迁移方式 |
| 检索 | 本地 multilingual embedding 模型与简单向量相似度检索 | 已确认E5-small首轮实验，具体效果、参数仍需验证 |
| 大模型 | 可配置 API 调用，同时支持测试替身 | 服务提供方、模型、预算、数据发送范围和配置 |
| 开发验证 | pytest、前端测试及 Git | 测试用例、检查入口和经授权的 Git 工作流程 |

用户已确认首轮规则检索实验采用 intfloat/multilingual-e5-small（MIT），Sentence Transformers及CPU版PyTorch在本地运行；公开模型文件从Hugging Face下载，规则和问题不上传，不调用收费API。规则向量索引保留原文与来源，具体版本、切分和开发集结果见DATA_DESIGN与本地报告。当前模型仅为可替换的实验选择，不预设优于关键词检索，也不代表已完成真实LLM问答。

用户确认保留向量检索能力及现有代码，作为长期处理长篇规则、攻略、背景资料的路径，不因小规模关键词对照结果删除。资料处理按特点组合三条路径：规整资料通过规则提取、校验后结构化保存；杂乱资料可由LLM辅助提取成指定字段再校验；长文保留正文与来源，切分并生成向量索引。三者可组合，不必把所有资料向量化或都塞进SQLite。DataProcessor负责共用的校验与输出，来源解析、LLM适配、数据库保存和向量索引保持独立职责；LLM整理目前只有接口与替身，真实服务尚未接入。向量化不等于摘要或事实审核，原文始终保留。

本地优先，不建设云服务器、账号登录、复杂 Agent 或重型基础设施。代码保持简单、模块化、可扩展，避免为未来游戏提前搭建复杂框架。

已确定的方向不反复当作未选方案讨论；具体模型、重大契约及外部调用等细节通过小规模验证与用户审查落实。API 方向不等于授权任意联网调用、发送资料或产生费用。测试替身用于稳定验证工程流程，真实模型效果单独验证。

| 2. 如何从抽象需求推导业务规则、数据结构、接口和测试；陌生技术如何验证？ | 结合具体输入输出解释推导过程；先提出规则和契约，再做最小实验或测试，记录结论与局限。 |
| 3. 如何比较语言、框架、数据库和模型方案，并记录技术选型理由？ | 保留已确定方案的理由与约束；需要新决策时给出有限候选、取舍和验证证据，用户作出决定。没有记录的历史理由不能补造。 |
| 4. 如何通过通用核心模块、游戏配置和适配层实现可扩展架构？ | 解释通用流程与游戏差异的边界；优先配置和小型适配，避免复制整套系统或预建复杂框架。 |
| 5. 如何编写有效开发提示词，维护持续有效的工程文档，而不是依赖聊天上下文？ | 任务提示词明确目标、范围、前置条件、涉及文件和验收方式；持续记录已确认决策、事实状态及待办。 |
| 6. 如何使用 Git 分支、Commit、Pull Request、代码审查和安全回滚？ | 在获得具体操作授权后分步实践，解释操作目的、可审查结果与恢复方式；不自动提交、推送或合并。 |

## 五、合作原则与实施节奏

- 每次仅开展一个明确的小任务。
- 实现之前解释目标、重要设计和预计修改的文件。
- 实现之后说明修改、测试、风险及用户的验收方式；没有执行的验证如实标明。
- 用户需要理解代码，不能只交付自动生成的结果。
- 新技术或工具先解释用途、在项目中的位置与验证方式，再安排用户的实际思考或操作。每项任务记录目标、范围、前置条件、双方任务、实际验证证据及审查状态；适用时先测试再实现，不照搬复杂企业流程，不新增重复文档。
- 不得虚构来源、测试结果、知识覆盖或评测结论。后续比较普通 LLM 与系统时，记录实际结果，不预设系统胜出。
- 未经确认不扩大范围，也不自动提交、推送或合并代码；Git 学习目标本身不代表已授权执行 Git 命令。
- 14 天计划表示任务实施顺序，不是不可调整的硬性期限；按依赖、验证和审查进度推进。
