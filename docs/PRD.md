# GameWise AI 产品需求文档

状态：产品范围与基础技术方向已确认；具体版本、资料准入、模型和量化门槛待确认。本文描述目标行为，不代表功能已经实现或通过测试。

## 1. 产品目标

为普通玩家提供本地运行的游戏攻略助手，围绕明确的游戏与版本检索经过审核的资料，回答有限主题的问题，并展示支持结论的证据。

使用统一提问入口，问答与比较均由自然语言问题表达。玩家可直接提问，单个 LLM 理解问题并选择受控只读工具；后端校验参数、分别检索各范围，再由 LLM 根据证据回答。手动范围选择作为辅助，不再是提问前置条件。已有三个工具及虚拟模型的本地预览，正式范围与接口仍待落实，真实LLM问答尚未实现。

2026-10-28 用户调整首批 MVP：专注三国杀 OL、十周年、移动版三个服，记录各服武将不同系列的技能，完成资料收集、范围内检索、有来源问答、真实跨服技能对照和 baseline/RAG 评测的完整实验。黑暗之魂 3（Dark Souls III）与艾尔登法环（Elden Ring）保留已有成果并延后，不计入当前首批验收；长期多游戏定位与可扩展架构不变。

通过固定题集对比普通 LLM 与 RAG 系统，检验事实准确性、引用支持度、版本隔离和证据不足处理；不预设 RAG 必然更好，不承诺消除全部错误。

## 2. 已确认技术与运行边界

| 项目 | 决策 |
| --- | --- |
| 前端 | React + TypeScript + Vite，本地网页 |
| 后端 | Python + FastAPI，Pydantic 数据校验，pytest 测试 |
| 原始资料 | Markdown / JSON |
| 结构化元数据 | 优先 SQLite |
| 检索 | 优先本地多语言 embedding 与简单向量相似度；具体模型实现前验证；不使用复杂向量数据库 |
| 回答 | 可配置 LLM API，必须有测试替身 |
| 运行 | 应用和资料存储在本机，不依赖付费云服务器；真实模型 API 可能需要联网并产生费用 |

模型提供方、数据发送范围、费用预算、embedding 下载及运行依赖须在使用前确认。替身用于验证流程，不能作为真实模型效果或真实 RAG 可用性的证明。

## 3. MVP 范围与资料状态

### 3.1 游戏登记

| 游戏 | 产品状态 | 具体版本与主题 | 真实知识库状态 |
| --- | --- | --- | --- |
| 三国杀 OL | 当前首批目标 | 武将各系列技能；模式与规则适用期逐项核对 | 已有批量待审资料；数量及缺口见PLAN，非正式知识库 |
| 三国杀十周年 | 当前首批目标 | 武将各系列技能；模式及规则适用期待核对 | 已有批量待审资料；数量及缺口见PLAN，非正式知识库 |
| 三国杀移动版 | 当前首批目标 | 武将各系列技能；目录、模式及规则适用期逐项核对 | 已有批量待审资料；数量及缺口见PLAN，尚未正式准入 |
| 黑暗之魂 3 | 延后，保留成果 | 平台、补丁、DLC 范围及主题待确认 | 有清单提取实验，未建立正式知识库 |
| 艾尔登法环 | 延后 | 平台、补丁、DLC 范围及主题待确认 | 尚未建立真实知识库 |

确认游戏名称不等于登记好完整版本，不等于获得资料，也不等于支持任意问题。后续目录按游戏、版本、审核状态、已验证主题、来源、缺口和资料快照记录覆盖情况。

通用目录按类别、具体作品或发行分支、规则版本及资料覆盖组织；三国杀增加有来源依据的武将与系列条目关联，并分别记录适用模式。比如“闪孙坚”“谋孙坚”须核实具体分支与页面，不能并入“孙坚”条目或仅靠前缀建立系列映射。经典、国战、1V1 不等于补丁版本；同名技能不能跨服、系列或模式补齐。默认三服和已明确的模式分别展示，不将可并列的候选一律当作歧义；真正不能确定的对象或规则范围再澄清。

首版按用户最新要求以工程闭环优先：从已有三服资料中选择可核对的武将、系列和模式演示集，并补充必要规则；具体清单与使用、规则范围须先由用户审查，不在此预设条目数量。全武将全系列作为后续覆盖目标，不阻塞首版。仍保留候选目录、发现/提取/审核/可回答数量和缺口，界面只宣称实际支持范围；不能把有限演示集、Wiki 目录或请求成功说成全覆盖。

未上线武将也保留收录，明确标注“未上线”及状态依据，与“已上线”“待确认”分开；资料审核状态另行管理。已明确待上线、页面写“敬请期待”的条目按核对结果标记，不因未上线删除，也不在回答中说成当前正式服已可用。用户已确认 OL 闪孙坚为已上线、移动版起孙坚为未上线；后续有上线证据再更新记录，不能仅凭页面日期自动改状态。

扩展以通用核心、游戏配置与必要适配层为边界。新增常规游戏应主要增加登记、审核资料、索引与测试，尽量复用核心；新领域确有特殊结构时另行审查小型适配。验收包含使用合成登记与资料验证非首批游戏可接入、旧范围不受污染，不能将此测试记为该游戏真实建库完成。具体字段在契约阶段确定。

### 3.2 首批功能

实施顺序：选定并审核首版演示集 → 补必要规则 → 验证受控工具流程 → 接获准的真实 LLM → 网页闭环和小规模评测。规则优先覆盖所选场景的身份/胜利条件、模式、牌与技能结算；不要求先建完专家策略库，也不扩大到无关趣闻。全量采集不再是主线前置条件，下载成功不等于完成结构化或准入。

比较验收加入“刘备和曹操谁适合做主公”场景：先检查双方在请求范围内的全部已核查系列、模式及缺口，分别取得技能和相关规则，再给分范围分析；条件不明确或资料不足时说明限制。数值强度、主公适应性、设计体验和人物还原分开评价，不能把“多摸牌/直伤”直接写成普遍更强的规则；人物背景与设计评价需要相应依据及明确标准。模拟阶段检查工具数据和取证流程，不能代替真实 LLM 能力评测；是否独立增加原文补查工具在实验任务中审查。

1. 核对三服武将、系列目录，分批自动整理经确认的技能资料为 Markdown / JSON；校验元数据，保存来源、审核及规则适用信息，统计覆盖与缺口。
2. 展示游戏、版本和真实资料覆盖状态。
3. 用户直接提问或辅助选择范围，LLM 请求调用查询工具，后端在明确且校验后的各范围内检索，生成带证据的回答。
4. 展示引用片段、来源和定位，区分事实、推断与策略建议。
5. 对版本缺失、无证据、已识别冲突、非法输入和服务故障显示明确状态。
6. 分别检索明确的服、系列条目及模式范围，在统一问答中完成至少一个双方有真实证据的跨服技能对照，不编造差异；原文相同也如实说明。
7. 提供固定题集、baseline / RAG 运行记录、自动检查和人工评分汇总。

资料准备以可复用处理类为入口，支持手动整理、规则提取和可选 LLM 辅助，输出结构由调用方定义，不把三国杀字段写死在核心。当前通过 Pydantic 类声明期望字段与类型，导出 JSON/Markdown；尚无界面编辑格式。来源归属、证据引用和审核状态为共同信息，游戏特有内容按类型定义。LLM 客户端接口默认关闭，用户已选择后续程序 API 调用方向，真实服务、模型、预算和发送范围另行确认；当前只用测试替身，不建设云服务器。结果经过共同校验与人工审核后才可进入资料库，转换成功不能视为已审核事实。

LLM 整理须保留原始资料和可追溯片段，未知项明确留空或列为无法处理，不能补造技能、来源、版本或上线结论，也不能自行提高审核状态。程序核对格式、归属、原文对应与批次完整性，人工核对内容支持关系；资料文本作为数据处理，不能覆盖转换指令。批量大小、超时、有限重试和费用控制在实现时明确，不默认将全部资料一次发送或失败无限重试。

首个实际闭环使用明确服、具体系列和规则范围的已审核资料完成可追溯问答，再扩展到所选演示集。首版交付须有三服实际覆盖记录、真实技能问答及至少一个真实跨服案例，并说明局限；不承诺专家级胜率、全武将排名或所有技能交互。已有曹操、刘备、孙坚相关资料可作为演示集候选，不等于其所有系列均已审核，最终条目清单尚未冻结。

首批采用单LLM的受控工具调用流程（ReAct思路，与前端React不同）：未指定服默认分别查询三服，指定服则限制范围。2026-11-18更新：人物比较/推荐未指定系列时，先发现对应服有来源且经核查的各系列候选，分层推荐；明确具体条目/系列则只比较所选，不默认缩成标准版或把候选都当别名。底层技能仍逐条精确读取，不同模式分开标注；强度与主公适配分开说明，无统计数据不宣称胜率排名。是否有主公技按具体技能判断，常备主公选将范围另需依据；常备清单暂不计入本次任务。候选发现、资料读取及模型正确比较分别验收，不能仅凭登记或查询成功宣称问答支持。未知规则范围不猜为最新版；跨服对照、范围隔离要求不变，跨游戏及完整历史版本对照延后，不建设多Agent或通用自主执行框架。

### 3.3 不纳入首批 MVP

魂系问答、跨游戏比较、自动从自然语言识别游戏及版本、完整历史版本对照属于后续增强，不计入首批交付。首批专注技能原文及证据支持的解释，不承诺全量技能交互推演、胜率判断、阵容推荐或皮肤、台词、充值活动资料。

云服务器部署、登录与账户、付费产品功能、多人协作、多 Agent 编排、复杂向量数据库、模型训练、大规模自动抓取、全游戏覆盖、实时画面分析、自动操作游戏、游戏内插件、复杂前端和资料管理后台。

“大规模自动抓取”指不建设无限制全站爬虫或重型采集基础设施；按已确认使用范围和三服目标目录分批自动读取、整理技能资料属于首批需要实现的能力。

## 4. 用户操作流程

### 4.1 单游戏问答

1. 打开本地页面，查看后端状态与游戏资料覆盖。
2. 可直接输入问题，也可辅助选择游戏和范围；页面展示系统实际采用的范围和覆盖。未指定服的三国杀问题按登记的三服分别查询，没有资料或未审核的范围显示缺口。
3. 输入问题并提交。已登记但无资料的范围应直接提示尚无资料。
4. 系统校验选择，在该游戏版本内检索；证据不足时显示不足，不用模型常识补齐确定事实。
5. 有证据时显示回答、适用范围及与具体结论关联的引用。
6. 展开引用查看片段、来源性质、定位、采集日期及原始链接或本地来源说明。
7. 需要澄清时选择版本或补充对象后重新提交。切换游戏时清除无效版本，避免保留旧答案造成误解。

### 4.2 统一问答中的跨服技能提问

1. 在同一入口输入比较问题，LLM 通过目录工具确定候选，再请求分别查询；用户可指定双方范围，无需先进入独立比较页面。真正不明确的对象或规则范围再澄清。
2. 使用有意义的共同维度组织回答，信息不足时澄清。首个验收主题由资料可用性决定，不提前虚构机制或数值。
3. 系统分别检索双方范围，在同一回答中清楚关联事实、证据及可比性限制；按内容需要使用文字或表格，不强制固定比较表。
4. 一方证据缺失时仅标记该侧不足，并将整体结果标为部分完成；不能推导该游戏没有相应机制。
5. 已识别冲突显示对应侧证据；不适用维度标为不适用，不强行给出高低排名。

### 4.3 资料审核流程

Codex 整理候选来源及可用性说明，用户确认来源可信度、使用依据与限制、平台补丁和 DLC 适用范围，再进入资料导入。待审、来源不明或范围未确认的内容不得参与正式问答。测试夹具只用于功能验证，不能计入真实知识库。

## 5. 版本感知与资料规则

### 5.1 必要数据概念

| 概念 | 必要信息与规则 |
| --- | --- |
| 游戏目录 | 类别、具体作品或发行分支、稳定标识、中英文名与别名；具体映射与字段待契约审查，不能将类别当作共享规则范围 |
| 版本范围 | 关联明确游戏或发行分支，记录平台、补丁、DLC 范围与确认依据；未知项明确记录，不推断适用 |
| 来源资料 | 能唯一识别资料，记录标题、主题、正文位置、来源定位与性质、采集和维护信息、使用依据与限制、审核状态及记录 |
| 适用映射 | 资料到明确版本记录的映射；跨版本映射逐项审核，不按版本号排序自动推断 |
| 检索片段 | 每个片段能够唯一识别，并回溯原始正文、章节或段落、来源及适用游戏版本 |
| 检索索引 | 能追踪所用片段、资料快照和生成配置；资料或模型变化时能够识别不兼容，避免继续使用过时结果 |
| 覆盖记录 | 每个游戏版本已审核资料、已验证主题、未覆盖内容及最近验证记录 |

具体 Pydantic / SQLite 结构与接口字段在第 2 阶段提交审查。索引可采用简单本地文件或 SQLite 配套存储，格式经验证后确定；模型或切分配置变化时检测不兼容并重建，不混用向量。

字段名称、数据关系和最小记录方案见 [数据设计草案](DATA_DESIGN.md)，审查通过后再实施；本节保留业务要求，不将候选字段当作已批准契约。

### 5.2 检索边界

- 游戏与版本是执行检索的强制条件，先过滤范围再计算相似度；相似内容不得绕过过滤。
- 未选服不直接判为需澄清：三国杀默认分别查三服。每次内容查询仍须有已核查规则范围；只有一个明确可用范围时可采用并展示，有多个无法并列说明的规则候选时澄清，未知或非法范围不得猜测。不同模式可分别展示，不能把模式当作补丁版本。
- 未登记版本不自动回退到“最新版”。资料没有明确适用映射时不得检索使用。
- 缓存和索引必须保持范围隔离；比较每侧分别限定范围。
- 相似度最高不等于存在足够证据。阈值、Top-K 及不足策略使用开发集校准并在独立评测前冻结。

### 5.3 来源与引用

- 来源可信、内容准确、使用方式允许、版本适用是分别检查的条件。公开网页或官方资料不自动意味着允许复制、保存、向 API 发送或再分发。
- 所需使用方式包括本地保存、切分建索引、发送模型 API、展示片段及可能提交仓库；逐项确认相关限制，无法确认时保留待审。
- 回答中的关键事实必须关联支持它的片段，前端展示可追溯来源。仅附一个相关主页不算合格引用。
- LLM 使用检索返回的引用 ID；后端验证 ID 与范围，再从资料记录生成链接。模型生成的未知 ID 或链接不得直接显示为可信引用。
- “引用合法”由程序检查，“证据支持结论”由人工核验与评测检查。不能仅凭引用结构有效就宣布事实正确。
- 推断、建议和已确认事实分开表述。来源冲突时保留差异，不拼成一个确定结论。
- MVP 处理人工标注和已识别冲突，不承诺穷尽所有自然语言冲突。

## 6. 接口与状态契约

以下为目标接口：当前仅 /health 已实现，catalog、ask 尚未实现；精确字段在第 2 阶段审查后确认。

| 接口 | 职责 |
| --- | --- |
| GET /health | 本地后端存活状态，不等于模型或知识库效果合格 |
| GET /api/catalog | 游戏、已登记版本、主题、资料覆盖及缺口 |
| POST /api/ask | 接收问题及可选范围约束，协调 LLM 选择受控查询工具；返回回答、实际范围、引用、澄清项或不足原因，保留各侧状态与完整性；字段待审查 |

问答业务状态：

| 状态 | 触发情形 | 用户可见行为 |
| --- | --- | --- |
| answered | 检索有支持证据且输出通过结构及引用检查 | 显示回答、范围、结论引用；事实支持度仍需评测 |
| needs_clarification | 默认三服和分模式展示仍无法消解的对象或规则歧义 | 给出有效选择；未指定服本身不触发此状态，不跨范围拼接事实 |
| insufficient_evidence | 无已审核资料、无有效召回或所需事实缺证据 | 明确不足和覆盖缺口，不编造确定事实 |
| conflicting_sources | 已识别的来源在同一适用范围内存在未解决冲突 | 展示冲突点及双方证据，不给无依据的确定结论 |

比较复用每侧证据状态，整体区分完整、部分完成、需要澄清和证据不足；每个维度可标记不适用。具体枚举在契约审查时固定。

技术错误使用独立的错误响应，包括错误代码、可理解提示与是否可重试：非法输入或范围、API 超时或鉴权失败、模型返回无效引用、embedding 未安装、索引缺失或不兼容、数据库故障等。不得显示为 answered，不得伪装成无证据。重试有上限，前端保留输入并提示下一步。

## 7. 验收标准

| 能力 | 必须提供的验收证据 |
| --- | --- |
| 本地运行 | 按 README 启动前后端；无需付费云服务器；模型和下载依赖明确 |
| 资料准入 | 三服各有经确认来源、使用范围及规则适用期的真实技能资料；保留审核记录 |
| 武将与系列覆盖 | 以用户审查的首版演示集为交付范围，逐项核对系列与模式；仍保留完整候选目录与缺口，不宣称全服覆盖；扩大范围另行验收 |
| 导入 | 合法资料可导入；缺必要信息被拒绝；重复导入不重复建档；待审资料不可回答 |
| 范围隔离 | 同名武将/技能、不同服/系列/模式、非法或缺失规则版本、缓存切换等确定性测试全部通过；歧义先澄清，不跨范围取证 |
| 可扩展性 | 用非首批游戏的合成配置和资料验证接入，无需为该游戏在核心添加专用分支；回归旧范围，真实覆盖与合成测试分别记录 |
| 本地检索 | 真实多语言 embedding 在本机验证中可运行；开发题的预期片段进入约定 Top-K，阈值和指标有记录 |
| 问答 | 三服各完成至少一个真实技能资料问答，且抽查不同系列；关键条件、对象、次数和数值与引用支持关系经人工审查，不仅展示“孙坚”单一页面 |
| 引用 | 程序校验存在性、本次检索归属和范围；人工逐条核验必验案例的关键事实，不允许伪造引用 |
| 异常 | 澄清、无证据、已识别冲突及服务故障有接口与页面验证；无证据不补造答案 |
| 跨服技能对照 | 至少一个真实跨服案例，双方条目、模式及规则范围明确，事实各有证据；原文相同不虚构差异，覆盖一侧不足测试 |
| 前端 | 类型检查、构建和关键组件验证通过；问答、澄清、不足、比较的端到端流程通过 |
| 评测 | baseline 与 RAG 运行可复查；同一基础模型、固定题集与共同配置，披露额外资料及差异，不预设胜出 |
| 交付 | 配置示例不含密钥；启动、导入、索引重建、人工验收和评测步骤完整；报告未完成项 |

确定性验证必须通过才可标记对应任务完成。生成效果的准确率、检索召回目标、引用支持率、延迟和费用门槛需在独立评测前确认，未达成或未确认时如实报告，不能宣布全部验收。

### 评测设计

Day 2 收尾设计已获用户认可：以 DATA_DESIGN 已讨论的 12 个问题作开发案例；独立评测计划 30 题，分为有证据技能问答 8、服/系列/模式/规则差异或歧义 6、证据不足 6、来源冲突 4、跨服对照 4、主观评价 2。后两道评价题检查事实与评价理由，不规定必须选同一名“最佳武将”。各题只归一个主要类别，可附风险标签；真实资料不支持的类别保持待补，不捏造冲突或标准答案，不从已公开开发案例复制独立题。真实题目、标准证据及合格门槛尚未冻结或验收。

建议分别报告以下维度，不先拼成一个掩盖问题的总分：

| 维度 | 提议判定规则 |
| --- | --- |
| 事实准确性 | 2＝必要事实正确完整，1＝部分正确但缺必要信息，0＝关键事实错误或编造；题目先列必要事实，无事实结论题不适用 |
| 范围隔离 | 通过＝事实来自正确服、具体系列、模式和规则范围且归属清晰；混用或用未知范围冒充确定范围记失败 |
| 引用支持 | 2＝关键事实均有支持证据，1＝仅部分得到支持，0＝不存在或不支持关键结论；无须给事实证据的纯澄清题不适用。baseline 未提供引用时记不适用，另统计虚构来源 |
| 不足与异常处理 | 应澄清、应说明不足、应展示冲突或应报告服务故障时行为正确才通过；正常有证据却拒答另记错误拒答。相关类别分别计算分母 |
| 主观评价 | 有明确评价标准、技能事实有依据、理由与事实一致且不编造胜率或共识才通过；不同偏好不直接判错，非评价题不适用 |

延迟、模型用量与费用另行记录，不与事实分数混加。题数、分母、评分理由和不适用项一并保留；具体准确率、召回、引用、延迟及费用合格门槛需在独立评测前另行确认，本提案不声称系统已经达标。

第 2 阶段确定类别、评分和划分；经审核的资料具备后、第 5 阶段真实检索调参前冻结独立题目、预期事实及来源。未具备真实资料的类别保持待补，不得伪称独立集已冻结或真实验证已完成。

记录每题预期行为、关键事实、来源定位、实际答案、检索结果和评分理由。事实准确性、引用支持度、版本错误、合理拒答、错误拒答与比较完整性分别统计；引用支持度仅对实际提供引用的方案统计，baseline 无引用记为不适用，另统计其虚构来源。报告题数和分母，不只报百分比。

baseline 不使用检索材料；RAG 使用相同问题、游戏版本提示、基础模型和共同生成配置并附检索证据。保存提示词、可获得的模型标识、资料快照、参数、耗时、用量、错误和人工评分。流程错误单独统计，不能静默剔除。独立结果查看后作出的修改以新实验记录，旧结果保留。

## 8. 实施节奏与未来扩展

PLAN.md 的 14 天表示 14 个实施阶段及依赖顺序，不是硬性工期。每次只做一个可审查的小任务；提前完成即可验收并推进，阻塞或审查未完成则顺延。额外功能需重新确认。

三国杀三服用于首批完整实验，通用核心不堆砌按服名判断的逻辑，领域差异放在资料适配层。后续恢复魂系或扩充技能交互等主题时，重新确认资料、使用范围和验收；不能因首批专注三国杀而改成只能处理三国杀的系统。
