# GameWise AI 产品需求文档

状态：产品范围与基础技术方向已确认；具体版本、资料准入、模型和量化门槛待确认。本文描述目标行为，不代表功能已经实现或通过测试。

## 1. 产品目标

为普通玩家提供本地运行的游戏攻略助手，围绕明确的游戏与版本检索经过审核的资料，回答有限主题的问题，并展示支持结论的证据。

使用统一提问入口，攻略与比较均由自然语言问题表达，不要求玩家先进入不同功能页面。首批仍手动明确一个或多个游戏及版本范围；涉及多个范围时分别检索并保留证据归属，不依赖自动识别游戏才能完成跨游戏提问。

首批实际建库目标为黑暗之魂 3（Dark Souls III）与艾尔登法环（Elden Ring）。MVP 必须完成一个双方都有真实审核资料支持的跨游戏比较案例。三国杀属于未来扩展，不计入首批验收。

通过固定题集对比普通 LLM 与 RAG 系统，检验事实准确性、引用支持度、版本隔离和证据不足处理；不预设 RAG 必然更好，不承诺消除全部错误。

## 2. 已确认技术与运行边界

| 项目 | 决策 |
| --- | --- |
| 前端 | React + TypeScript + Vite，本地网页 |
| 后端 | Python + FastAPI，Pydantic 数据校验，pytest 测试 |
| 原始资料 | Markdown / JSON |
| 结构化元数据 | 优先 SQLite |
| 检索 | 优先本地多语言 embedding 与简单向量相似度；具体模型实现前验证；不使用复杂向量数据库 |
| 回答 | 可配置 LLM API，必须有测试替身 |
| 运行 | 应用和资料存储在本机，不依赖付费云服务器；真实模型 API 可能需要联网并产生费用 |

模型提供方、数据发送范围、费用预算、embedding 下载及运行依赖须在使用前确认。替身用于验证流程，不能作为真实模型效果或真实 RAG 可用性的证明。

## 3. MVP 范围与资料状态

### 3.1 游戏登记

| 游戏 | 产品状态 | 具体版本与主题 | 真实知识库状态 |
| --- | --- | --- | --- |
| 黑暗之魂 3 | 首批建库目标已确认 | 平台、补丁、DLC 范围及主题待确认 | 尚未建立，未确认可用资料 |
| 艾尔登法环 | 首批建库目标已确认 | 平台、补丁、DLC 范围及主题待确认 | 尚未建立，未确认可用资料 |
| 三国杀 | 未来扩展目标 | 发行分支、规则版本和主题以后确认 | 不属于首批 MVP |

确认游戏名称不等于登记好完整版本，不等于获得资料，也不等于支持任意问题。后续目录按游戏、版本、审核状态、已验证主题、来源、缺口和资料快照记录覆盖情况。

目录按“类别 → 具体游戏或发行分支 → 版本 → 资料覆盖”组织。例如魂系类别可逐步登记黑暗之魂 1/2/3 等作品；三国杀可分别登记 OL、十周年等发行分支，各分支内部继续区分规则更新范围。分类不表示规则通用，同名武将或技能不得跨分支补齐事实。上述示例不代表已建库或增加首批交付范围。

扩展以通用核心、游戏配置与必要适配层为边界。新增常规游戏应主要增加登记、审核资料、索引与测试，尽量复用核心；新领域确有特殊结构时另行审查小型适配。验收包含使用合成登记与资料验证非首批游戏可接入、旧范围不受污染，不能将此测试记为该游戏真实建库完成。具体字段在契约阶段确定。

### 3.2 首批功能

1. 导入少量经过用户确认的 Markdown / JSON 资料，校验元数据，保存来源、审核及版本信息。
2. 展示游戏、版本和真实资料覆盖状态。
3. 用户选择游戏版本并提问，系统在指定范围内检索，生成带证据的回答。
4. 展示引用片段、来源和定位，区分事实、推断与策略建议。
5. 对版本缺失、无证据、已识别冲突、非法输入和服务故障显示明确状态。
6. 分别检索两个游戏，按统一维度展示一个真实跨游戏比较案例。
7. 提供固定题集、baseline / RAG 运行记录、自动检查和人工评分汇总。

首个可测试切片是一个已确认版本、一份审核资料、一个主题、一次可追溯问答。最终 MVP 需要覆盖两款游戏各自的有限主题与跨游戏案例，不要求完整攻略。

首批 MVP 以用户手动选择游戏和版本为主；自动从自然语言识别游戏及版本属于后续增强。首批必须完成至少一个双方真实审核资料支持的跨游戏比较；完整的跨版本结构化比较属于后续增强，但版本隔离测试仍是首批必验项，不能因推迟比较功能而省略。

### 3.3 不纳入首批 MVP

自动从自然语言识别游戏及版本、完整的跨版本结构化比较属于后续增强，不计入首批交付。

云服务器部署、登录与账户、付费产品功能、多人协作、多 Agent 编排、复杂向量数据库、模型训练、大规模自动抓取、全游戏覆盖、实时画面分析、自动操作游戏、游戏内插件、复杂前端和资料管理后台。

## 4. 用户操作流程

### 4.1 单游戏问答

1. 打开本地页面，查看后端状态与游戏资料覆盖。
2. 选择游戏和明确版本；页面显示平台、补丁、DLC 范围及支持主题。没有完成版本登记时不显示为可用知识库。
3. 输入问题并提交。已登记但无资料的范围应直接提示尚无资料。
4. 系统校验选择，在该游戏版本内检索；证据不足时显示不足，不用模型常识补齐确定事实。
5. 有证据时显示回答、适用范围及与具体结论关联的引用。
6. 展开引用查看片段、来源性质、定位、采集日期及原始链接或本地来源说明。
7. 需要澄清时选择版本或补充对象后重新提交。切换游戏时清除无效版本，避免保留旧答案造成误解。

### 4.2 统一问答中的跨游戏提问

1. 在同一问答入口手动明确双方游戏和版本，输入包含比较意图与对象的问题；具体范围选择交互在实施前审查。
2. 使用有意义的共同维度组织回答，信息不足时澄清。首个验收主题由资料可用性决定，不提前虚构机制或数值。
3. 系统分别检索双方范围，在同一回答中清楚关联事实、证据及可比性限制；按内容需要使用文字或表格，不强制固定比较表。
4. 一方证据缺失时仅标记该侧不足，并将整体结果标为部分完成；不能推导该游戏没有相应机制。
5. 已识别冲突显示对应侧证据；不适用维度标为不适用，不强行给出高低排名。

### 4.3 资料审核流程

Codex 整理候选来源及可用性说明，用户确认来源可信度、使用依据与限制、平台补丁和 DLC 适用范围，再进入资料导入。待审、来源不明或范围未确认的内容不得参与正式问答。测试夹具只用于功能验证，不能计入真实知识库。

## 5. 版本感知与资料规则

### 5.1 必要数据概念

| 概念 | 必要信息与规则 |
| --- | --- |
| 游戏目录 | 类别、具体作品或发行分支、稳定标识、中英文名与别名；具体映射与字段待契约审查，不能将类别当作共享规则范围 |
| 版本范围 | version_id、game_id、平台、补丁、DLC 范围与确认依据；未知项明确记录，不推断适用 |
| 来源资料 | ID、标题、主题、Markdown / JSON 内容路径、URL 或本地定位、来源类型、采集日期、内容标识、使用依据与限制、审核状态和记录 |
| 适用映射 | 资料到明确版本记录的映射；跨版本映射逐项审核，不按版本号排序自动推断 |
| 检索片段 | chunk_id、来源 ID、正文、章节或段落定位、游戏版本范围、正文标识 |
| 检索索引 | 关联片段 ID、资料快照、embedding 模型及修订、向量维度和切分配置 |
| 覆盖记录 | 每个游戏版本已审核资料、已验证主题、未覆盖内容及最近验证记录 |

具体 Pydantic / SQLite 结构与接口字段在第 2 阶段提交审查。索引可采用简单本地文件或 SQLite 配套存储，格式经验证后确定；模型或切分配置变化时检测不兼容并重建，不混用向量。

### 5.2 检索边界

- 游戏与版本是执行检索的强制条件，先过滤范围再计算相似度；相似内容不得绕过过滤。
- 版本未选择、未知或不属于该游戏时，先澄清或报错。即使只有一个资料版本，也需在界面明确展示并由用户确认选择。
- 未登记版本不自动回退到“最新版”。资料没有明确适用映射时不得检索使用。
- 缓存和索引必须保持范围隔离；比较每侧分别限定范围。
- 相似度最高不等于存在足够证据。阈值、Top-K 及不足策略使用开发集校准并在独立评测前冻结。

### 5.3 来源与引用

- 来源可信、内容准确、使用方式允许、版本适用是分别检查的条件。公开网页或官方资料不自动意味着允许复制、保存、向 API 发送或再分发。
- 所需使用方式包括本地保存、切分建索引、发送模型 API、展示片段及可能提交仓库；逐项确认相关限制，无法确认时保留待审。
- 回答中的关键事实必须关联支持它的片段，前端展示可追溯来源。仅附一个相关主页不算合格引用。
- LLM 使用检索返回的引用 ID；后端验证 ID 与范围，再从资料记录生成链接。模型生成的未知 ID 或链接不得直接显示为可信引用。
- “引用合法”由程序检查，“证据支持结论”由人工核验与评测检查。不能仅凭引用结构有效就宣布事实正确。
- 推断、建议和已确认事实分开表述。来源冲突时保留差异，不拼成一个确定结论。
- MVP 处理人工标注和已识别冲突，不承诺穷尽所有自然语言冲突。

## 6. 接口与状态契约

以下为目标接口，尚未实现；精确字段在第 2 阶段确认。

| 接口 | 职责 |
| --- | --- |
| GET /health | 本地后端存活状态，不等于模型或知识库效果合格 |
| GET /api/catalog | 游戏、已登记版本、主题、资料覆盖及缺口 |
| POST /api/ask | 统一接收攻略与比较问题及一个或多个明确范围；返回回答、范围归属引用、澄清项或不足原因；涉及多范围时保留各侧状态与完整性，字段待审查 |

问答业务状态：

| 状态 | 触发情形 | 用户可见行为 |
| --- | --- | --- |
| answered | 检索有支持证据且输出通过结构及引用检查 | 显示回答、范围、结论引用；事实支持度仍需评测 |
| needs_clarification | 缺少影响回答的游戏、版本或对象 | 提示补充并给出有效选择；不先跨范围生成 |
| insufficient_evidence | 无已审核资料、无有效召回或所需事实缺证据 | 明确不足和覆盖缺口，不编造确定事实 |
| conflicting_sources | 已识别的来源在同一适用范围内存在未解决冲突 | 展示冲突点及双方证据，不给无依据的确定结论 |

比较复用每侧证据状态，整体区分完整、部分完成、需要澄清和证据不足；每个维度可标记不适用。具体枚举在契约审查时固定。

技术错误使用独立的错误响应，包括错误代码、可理解提示与是否可重试：非法输入或范围、API 超时或鉴权失败、模型返回无效引用、embedding 未安装、索引缺失或不兼容、数据库故障等。不得显示为 answered，不得伪装成无证据。重试有上限，前端保留输入并提示下一步。

## 7. 验收标准

| 能力 | 必须提供的验收证据 |
| --- | --- |
| 本地运行 | 按 README 启动前后端；无需付费云服务器；模型和下载依赖明确 |
| 资料准入 | 两款游戏至少各有一组经确认来源、使用范围和版本的真实资料；保留审核记录 |
| 导入 | 合法资料可导入；缺必要信息被拒绝；重复导入不重复建档；待审资料不可回答 |
| 游戏版本隔离 | 同名实体、非法版本、缺版本、缓存切换等确定性测试全部通过；不跨范围取证 |
| 可扩展性 | 用非首批游戏的合成配置和资料验证接入，无需为该游戏在核心添加专用分支；回归旧范围，真实覆盖与合成测试分别记录 |
| 本地检索 | 真实多语言 embedding 在本机验证中可运行；开发题的预期片段进入约定 Top-K，阈值和指标有记录 |
| 问答 | 两款游戏各完成至少一个有限主题的真实资料问答；关键事实与引用支持关系经人工审查 |
| 引用 | 程序校验存在性、本次检索归属和范围；人工逐条核验必验案例的关键事实，不允许伪造引用 |
| 异常 | 澄清、无证据、已识别冲突及服务故障有接口与页面验证；无证据不补造答案 |
| 跨游戏比较 | 至少一个黑暗之魂 3 与艾尔登法环的真实案例，双方版本明确、共同维度成立、事实各有证据；覆盖一侧不足测试 |
| 前端 | 类型检查、构建和关键组件验证通过；问答、澄清、不足、比较的端到端流程通过 |
| 评测 | baseline 与 RAG 运行可复查；同一基础模型、固定题集与共同配置，披露额外资料及差异，不预设胜出 |
| 交付 | 配置示例不含密钥；启动、导入、索引重建、人工验收和评测步骤完整；报告未完成项 |

确定性验证必须通过才可标记对应任务完成。生成效果的准确率、检索召回目标、引用支持率、延迟和费用门槛需在独立评测前确认，未达成或未确认时如实报告，不能宣布全部验收。

### 评测设计

建议独立评测集 30 题：有证据问答 10、版本差异或歧义 6、证据不足 6、来源冲突 4、跨游戏比较 4。此题量与分布是待确认建议，资料不足时调整并记录，不编造所谓标准答案。另建开发集用于调试。

第 2 阶段确定类别、评分和划分；经审核的资料具备后、第 5 阶段真实检索调参前冻结独立题目、预期事实及来源。未具备真实资料的类别保持待补，不得伪称独立集已冻结或真实验证已完成。

记录每题预期行为、关键事实、来源定位、实际答案、检索结果和评分理由。事实准确性、引用支持度、版本错误、合理拒答、错误拒答与比较完整性分别统计；引用支持度仅对实际提供引用的方案统计，baseline 无引用记为不适用，另统计其虚构来源。报告题数和分母，不只报百分比。

baseline 不使用检索材料；RAG 使用相同问题、游戏版本提示、基础模型和共同生成配置并附检索证据。保存提示词、可获得的模型标识、资料快照、参数、耗时、用量、错误和人工评分。流程错误单独统计，不能静默剔除。独立结果查看后作出的修改以新实验记录，旧结果保留。

## 8. 实施节奏与未来扩展

PLAN.md 的 14 天表示 14 个实施阶段及依赖顺序，不是硬性工期。每次只做一个可审查的小任务；提前完成即可验收并推进，阻塞或审查未完成则顺延。额外功能需重新确认。

未来三国杀扩展将沿用资料准入、版本隔离、引用及评测框架，并单独登记具体发行分支、规则版本、技能文本和规则交互。届时重新确定来源、许可、主题与测试，不默认不同三国杀版本共享规则，也不为此提前建设复杂架构。

## 9. 尚待确认与当前事实

需要用户确认：
1. 两款游戏的平台、补丁版本、DLC 范围、首个查询主题及跨游戏比较对象和维度。
2. 真实资料的候选来源、可信度、使用依据、允许操作及版本适用性。
3. 本地 embedding 的具体模型、许可、下载体积、硬件需求和效果验证结果。
4. LLM API 提供方、模型、配置、费用预算、数据发送范围与日志要求。
5. 具体数据与接口结构、前端测试依赖、评测题量和量化门槛。

当前已实现后端 /health 及本地状态页面，相关自动检查与 Codex 浏览器验证通过；前后端用户运行验证通过，改动审查与 Day 1 整体验收待完成。尚未确认可用真实资料、建立知识库或实现游戏问答接口。后续完成情况以 PLAN.md 的实际验证记录和用户验收为准。
